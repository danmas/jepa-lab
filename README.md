# jepa-lab

Учебная лаборатория **JEPA** (Joint Embedding Predictive Architecture) на CPU, без GPU.

Два эксперимента в одном репозитории:

1. **«Воображение»** — модель катит мир вперёд в латентном пространстве и не разваливается.
2. **«Цель словами»** — фраза → план в латенте → мяч в нужной зоне. Пиксели в поиске
   не участвуют; LLM (или таблица) только ставит цель и читает отчёт.

Ядро — 0.94M параметров, кадры 64×64, весь мир генерируется кодом (датасета на диске нет).

## Простыми словами

Ты говоришь модели «мяч в верхний левый угол» — и она сама:

- **понимает, куда попасть**: фраза → таблица зон → кадр-цель → `E_ema` → `z_goal` (48 чисел);
- **перебирает сотни вариантов** «если толкнуть так, потом так, потом эдак» —
  128 планов × 8 итераций = **1024 раскатки**, каждая целиком в латенте;
- **выбирает лучшую последовательность** толчков по стоимости `‖z_H − z_goal‖`;
- **толкает мяч и перепланирует на каждом шаге** (MPC) — план не догма, он правится по факту;
- **доводит мяч до зоны примерно в 8 случаях из 10** (82% на 90 эпизодах; при хаотичных
  отскоках 100% не бывает — и это честная цифра, а не обещание);
- **отдаёт отчёт словами**: «мяч примерно в (20, 21), цель достигнута».

Будущие кадры она **не рисует** — думает только 48 числами. Поэтому решение занимает
**~70 мс** на обычном процессоре, а не 8.5 с, как у планировщика по пикселям.

Это и есть демонстрация: модель научилась не просто предсказывать кадры,
а **планировать действия ради цели**.

```bash
pip install -r requirements.txt

# обучение двух моделей (jepa и пиксельный baseline), ~22 мин на CPU

python train.py --mode pixel --steps 2500 --tag v4

# голова «латент -> слова»
python probe.py --tag v4

```

## Эксперимент 2: планирование в латенте (v0.3)

### Как это устроено

```
«положи мяч в правый верхний угол» ──► таблица зон ──► кадр-цель ──► E_ema ──► z_goal
                                                                                 │
CEM: 128 последовательностей действий × 8 итераций, раскатка на 10 шагов ◄────────┘
      стоимость = ||z_H − z_goal||² + 0.3·mean(последние 3)      ← пиксели не участвуют
                    │
                    ▼
     MPC: выполняем первое действие, перепланируем от настоящих кадров
                    │
                    ▼
     probe: (z_{t-1}, z_t) ──► (x, y, vx, vy) ──► слова
```

| Слой | Кто делает | Учится |
|------|-----------|--------|
| Слова → зона | таблица 9 зон + синонимы (`data.find_zone`) | нет |
| Динамика и поиск | JEPA-модель + CEM | **да** |
| Латент → слова | `Probe` (ridge-регрессия) | да, 1 минута |

LLM в латент не залезает: он ставит цель и читает отчёт. В этой версии его роль играет
таблица — чтобы демо работало без API.

### Два режима стоимости (`--cost`)

| Режим | Стоимость плана | Зачем |
|-------|-----------------|-------|
| `latent` (по умолчанию) | `‖z_H − z_goal‖²` + штраф за последние 3 шага | чистый JEPA: никаких дополнительных голов, только латент |
| `mixed` | то же + `0.01·‖probe(z_H).xy − центр зоны‖²` | калиброванная стоимость: позиция мяча входит явно |

Запуск:

```bash
python plan.py --goal "в центр" --cost latent
python plan.py --goal "в центр" --cost mixed --probe-weight 1.0
python eval.py --tag v4 --cost latent      # таблица ниже
python eval.py --tag v4 --cost mixed
python chat.py --cost mixed                 # то же и в чате
```

### Результаты (9 зон × 10 стартов = 90 эпизодов, H=10, CEM 128×8)

| | `latent` | `mixed` | случайные действия | пиксельный CEM |
|---|---|---|---|---|
| успех | **82%** | **73%** | 36% | 50%* |
| время решения (медиана) | **70 мс** | **71 мс** | — | **8480 мс** |
| p90 | 85 мс | 84 мс | — | — |
| корреляция стоимость↔промах (Спирмен) | −0.03 | **+0.17** | — | — |

\* пиксельный CEM прогнан всего на 2 эпизодах (8.5 с на решение), поэтому его успех
не сравнивать с 90 эпизодами — сравнима только скорость, и она измерена точно.

**Что из этого следует:**

- Латентный поиск решает задачу: **82% против 36%** у случайных действий, при 70 мс
  на решение. Перебор 1280 воображаемых будущих укладывается в одну десятую секунды.
- Пиксельный планировщик на ту же задачу тратит **8.5 секунды** на решение — в ~120 раз
  больше. Это и есть ответ на вопрос «зачем предсказывать в латенте».
- **Разница в успехе между `latent` и `mixed` статистически незначима**: на разных
  прогонах 70–86% и 73–80% (мир хаотичен из-за отскоков, ±8 п.п. от прогона к прогону).
  Выбор режима — не про успех.
- **А вот калибровка различается системно**: корреляция стоимости с реальным промахом
  у `mixed` положительная и устойчиво выше (−0.03 → +0.17). То есть `mixed`-стоимость
  честнее предсказывает, какой план действительно лучше, а `latent` — «слепая», но
  за счёт замкнутого контура (перепланирование каждый шаг) успех тот же.

**Практический вывод:** если нужен чистый JEPA-нарратив без лишних голов — `latent`;
если стоимость плана будет использоваться ещё где-то (ранняя остановка поиска,
сравнение планов между собой) — `mixed`.

### Голова «латент → слова» (`probe.py`)

Ridge-регрессия по паре латентов `(z_{t-1}, z_t)` на замороженном энкодере:

| величина | R² | MAE |
|----------|----|-----|
| x | 0.9992 | 0.33 px |
| y | 0.9992 | 0.35 px |
| vx | 0.9805 | 0.41 px/кадр |
| vy | 0.9790 | 0.43 px/кадр |

Пара латентов, а не один: в одном кадре скорости физически нет (мяч симметричен) —
по одному латенту `vx/vy` дают R² ≈ 0.

## Эксперимент 1: «воображение» без действий (v0.2)

Две одинаковые модели предсказывают следующий кадр — одна эмбеддинг, другая пиксели.
Раскатка на 30 шагов без единого реального кадра (промах мяча в пикселях):

| шаг | JEPA | пиксельная |
|----:|-----:|-----------:|
| 1 | 1.5 px | 1.5 px |
| 5 | 4.2 px | 3.8 px |
| **10** | **0.8 px** | **6.2 px** |
| 15 | 6.5 px | 10.9 px |
| 30 | 34.5 px | 29.7 px |

Честный вывод того эксперимента: латентная раскатка точнее на среднем горизонте в 2–8 раз,
но **размытия у пиксельной модели не появилось** (разброс пятна 2.90–3.02 против 2.87
у реальных кадров) — мир детерминированный и без неоднозначности, а без неё MSE-оптимум
не размывается. Подробности и что нужно, чтобы размытие воспроизвести —
`KB/README_DEV.md`.

## Что здесь «по-настоящему от JEPA», а что упрощено

- **По-настоящему:** предсказание в латентном пространстве, EMA-цель со stop-grad,
  раскатка без возврата в пиксели, планирование перебором в латенте.
- **Упрощено:** в лоссе есть реконструкция кадра (иначе предсказанный латент нечем
  показать) — это ближе к world-model-автоэнкодеру (Dreamer), чем к чистому I-JEPA.
  Мир игрушечный: 0.94M параметров, 64×64, один объект, 9 дискретных действий.

Настоящие модели: [facebookresearch/ijepa](https://github.com/facebookresearch/ijepa),
[vjepa2](https://github.com/facebookresearch/vjepa2). На этом CPU готовый I-JEPA ViT-H/16
запускается как инференс — **7.8 с на картинку 448×448**; V-JEPA2 ViT-L —
**22.8 с на клип из 16 кадров**.
