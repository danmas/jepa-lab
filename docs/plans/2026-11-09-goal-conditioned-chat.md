# v0.3 — Целевое планирование в латенте + текстовый интерфейс

> **Статус:** предложение, на обсуждении. Код не писался.
> **Для Hermes:** после согласования — реализовывать по задачам из раздела «Этапы».

**Цель:** научить модель не просто «катить мир вперёд», а **достигать цели, заданной словами**:
«положи мяч в правый верхний угол» → модель перебирает варианты будущего в латентном
пространстве, выбирает действия, показывает раскатку и отвечает словами, где мяч.

**Архитектура в одну фразу:** JEPA-модель становится **action-conditioned** (предиктор
получает действие), цель задаётся **латентным эмбеддингом картинки-цели**, поиск действий —
**CEM + MPC перепланирование** целиком в латенте; текст разбирается детерминированной
таблицей зон, обратный отчёт — линейным probe из латента в физические координаты.

**Стек:** тот же (torch CPU, numpy, pillow, matplotlib). Новых зависимостей нет. GPU не нужен.

---

## 1. Почему именно так (ответ на вопрос про «LLM-переводчик»)

Разговор с миром состоит из трёх слоёв, и LLM нужен только в двух из них — но **не** внутри
латентного пространства:

```
твои слова  ──[слой 1: смысл]──►  цель (зона 16×16 на карте)
                                      │
                                      ▼
                              кадр-цель → E_ema → z_goal     (48 чисел)
                                      │
твои слова  ──[слой 2: поиск]──►  CEM: 128×8 воображаемых будущих в латенте
                                      │  (пиксели не участвуют)
                                      ▼
                              лучшая последовательность действий
                                      │
                                      ▼
                              реальный мир: выполняем 1-е действие, перепланируем
                                      │
                                      ▼
                    probe: z → (x, y, vx, vy) ──[слой 3: слова]──► «мяч в (11, 29), летит вниз»
```

| Слой | Кто делает | Учится? |
|------|-----------|---------|
| Смысл (слова → цель) | таблица из 9 зон + синонимы | нет, детерминированно |
| Динамика и поиск | JEPA-модель + CEM | **да**, это единственное обучение |
| Отчёт (латент → слова) | линейный probe + форматирование | да, 1 минута, закрытая форма |

Честная оговорка: в реальных системах слой 1 делает LLM (и он же часто вызывает инструменты
слоя 2). У нас там таблица — чтобы демо было без API и воспроизводимо. Именно это разделение
и есть суть: **LLM не переводит слова в векторы мира, он ставит цель и читает отчёт**.

## 2. Мир v2 — появляется управление (`data.py`)

Без действий планировать нечего. Добавляем импульс.

| Параметр | Значение | Почему |
|----------|----------|--------|
| Действие `u_t` | 9 вариантов: `(dx, dy) ∈ {-1,0,+1}²` | интерпретируемо («вправо», «вверх»), категориально для CEM |
| Сила импульса | 1.2 px/кадр к скорости | заметно, но не ломает физику |
| Гравитация | 0.4 (как сейчас) | верхние цели требуют борьбы с ней — интересно |
| Отскоки | упругие (как сейчас) | предсказуемость |
| Кадр | 64×64, 1 канал, [-1, 1] | без изменений |

`simulate(batch, horizon, rng, actions)` — действия случайные при генерации данных
(обучение под «случайную политику»), батч возвращает кадры + действия + истинные состояния.

**Альтернатива, от которой отказались:** непрерывный 2D-импульс. Плавнее и «правильнее», но
CEM по непрерывному дороже, а демо хуже читается словами.

## 3. Модель v3 — action-conditioned (`models.py`)

| Компонент | Изменение |
|-----------|-----------|
| `Encoder` | без изменений (64×64 → 48) |
| `Predictor` | **новый вход** `a`: `P(z_{t-1}, z_t, a) → z_{t+1}`; `a` — обучаемый эмбеддинг 9 действий в 16-dim, конкатенация |
| `Decoder` | без изменений (нужен только для глаз) |
| `EMATarget` | без изменений |
| `Probe` | **новый**: `Linear(48 → 4)` → `(x, y, vx, vy)`, обучается после модели, на замороженных латентах, закрытой формой (ridge) |

Лосс: раскатка **3 шага** (`HORIZON = 6`: 2 кадра контекста + 3 цели), каждое действие из
последовательности случайных действий.

```
l1 = MSE(P(z0, z1, a2),        sg(E_ema(x2)))
l2 = MSE(P(z1, ẑ2, a3),        sg(E_ema(x3)))
l3 = MSE(P(ẑ2, ẑ3, a4),        sg(E_ema(x4)))
loss = l1 + 0.5·l2 + 0.25·l3 + 0.5·rec + 0.05·var
```

**Почему 3 шага, а не 1:** планировщик будет крутить 10 шагов по своим предсказаниям; чем
длиннее раскатка в лоссе, тем меньше дрейф (в v0.2 уже видели: 1 шаг в лоссе → дрейф втрое хуже).

Стоимость: шаг обучения ~0.4–0.5 с → 2500 шагов ≈ 20 мин на CPU.

## 4. Цель — это картинка, а не команда (`data.py`, `plan.py`)

Девять зон 3×3, каждая 16×16 в кадре 64×64.

```
z_goal = E_ema(goal_frame),  где goal_frame = мяч в центре зоны (без маркера!)
```

**Почему без маркера:** мир не знает ни про какие маркеры — рамку зоны рисует только код
визуализации, уже поверх готовой картинки. Иначе энкодер увидит объект, которого в его опыте
не было.

Текстовая таблица (слой 1):

| Фраза (пример) | Зона (центр) |
|----------------|--------------|
| «левый верхний угол», «слева сверху» | (14, 14) |
| «центр», «посередине» | (32, 32) |
| «правый нижний», «вниз-вправо» | (50, 50) |
| … ещё 6 вариантов | … |

## 5. Планировщик — CEM + MPC (`plan.py`)

**CEM (cross-entropy method)** по категориальному распределению на 9 действий:

- горизонт `H = 10` шагов;
- 128 сэмплов, 8 итераций, элита 16;
- стоимость: `||z_H − z_goal||² + 0.3 · mean(||z_{H-2..H} − z_goal||²)`
  (второе слагаемое — чтобы не «пролететь мимо» на последнем шаге);
- всё считается батчем в латенте: 128×10 шагов предиктора = один небольшой MLP-прогон.

**MPC:** выполняем **только первое** действие, доезжаем реальный мир на шаг, перепланируем
от свежих настоящих кадров. Это защита от дрейфа и от off-policy (планировщик может искать
последовательности, которых не было в обучении).

**Оценка стоимости на CPU (прикидка):** 128 сэмплов × 10 шагов × MLP 48→512→512→48
≈ 0.65 GFLOP на итерацию; 8 итераций ≈ 5 GFLOP → ~1–2 с на решение. Для демо приемлемо.
Пиксельному планировщику на то же самое нужно 1280 прогонов декодера — это на порядок дороже,
именно это и показывает выгоду латентного мира.

## 6. Что меряем (`eval.py`)

| Метрика | Как |
|---------|-----|
| **success rate** | 30 случайных стартов × 5 зон; мяч в зоне на шаге H. Проверка — на **реальном симуляторе**, не в латенте |
| случайные действия | baseline: тот же бюджет шагов, действия случайные |
| время решения | мс на одно перепланирование (медиана, p90) |
| качество латентной стоимости | корреляция Спирмена между cost плана и реальным промахом в пикселях |
| (опция) пиксельный планировщик | тот же CEM, но cost по кадрам — success rate + время |

## 7. Артефакты и UX

python probe.py                                   # 1 мин: ridge 48 → (x, y, vx, vy)
python chat.py                                    # REPL: пиши фразой
python plan.py --goal "правый верхний" --steps 30 # без чата

## 8. Риски — и что делаем

| Риск | Оценка | Мера |
|------|--------|------|
| Латентная стоимость обманывает (средний латент при неопределённости) | средняя | меряем корреляцию cost ↔ реальный промах; если плохо — cost через probe + штраф за латент |
| Off-policy: планировщик ищет редкие последовательности | средняя | MPC (перепланирование каждый шаг), H=10, 3 шага раскатки в лоссе |
| Цель в верхнем углу недостижима при гравитации | низкая | сила импульса 1.2; если нет — поднять до 1.6 или сдвинуть зоны |
| Обучение подорожает | высокая | HORIZON=6, 2500 шагов ≈ 20 мин (приемлемо) |
| CEM медленный | низкая | батч, 128×8; при >3 с — уменьшить до 64×6 |

Итого: ~3 часа работы, ~50 мин машинного времени.

## 10. Чего в v0.3 НЕ будет (YAGNI)

- вызовов LLM внутри демо (слой 1 — таблица; LLM подключается снаружи без изменений кода);
- обучения политики (RL/BC) — только планирование;
- непрерывных действий;
- окклюзий, текстуры, двух мячей — это отдельная ветка экспериментов про размытие (v0.4).
